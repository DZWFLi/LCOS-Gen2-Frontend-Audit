## 1.4 修一个 patch 里仍然存在的 entity collision

当前 `ReconciliationRunner` 把 artifact 和 conversation 都塞进：


```ts

function entityKey(entityType: string, entityId: string): string {
```

```ts
for (const binding of artifactBindings) {

    entityKey(binding.entityType, binding.entityId),
    binding.spatialId,
  );
}
```

conversation 同理。

relation：

```ts
const fromNode = nodeIdByEntity.get(
  entityKey(String(rel.sourceEntityType), String(rel.sourceEntityId)),

const toNode = nodeIdByEntity.get(
  entityKey(String(rel.targetEntityType), String(rel.targetEntityId)),
);
```

## 1.5 `projectToSpaceProjection.ts`：不要只 `console.warn`

Patch 当前做法是：

```ts
try create A
catch -> console.warn
继续 create B
```

方向没错，但它把 partial failure 吞掉了。

不要直接把 `projectBatch()` 的返回类型全部推翻，避免波及所有 caller。

### 推荐加一个详细回执层

在：

```text
apps/web-gen2/src/spatial/projectToSpaceProjection.ts
```

新增：

```ts
export interface ProjectionItemFailure {
  readonly entityType: EntityType;
  readonly entityId: string;
  readonly message: string;
}

export interface ProjectionBatchReport {
  readonly bindings: readonly ProjectionBinding[];
  readonly failures: readonly ProjectionItemFailure[];
}
```

新增详细 API：

```ts
async projectBatchWithReport(
  inputs: SpaceEntityProjectionSource[],
): Promise<ProjectionBatchReport>
```

已有 API 保持兼容：

```ts
async projectBatch(inputs: SpaceEntityProjectionSource[]): Promise<ProjectionBinding[]> {
  return [...(await this.projectBatchWithReport(inputs)).bindings];
}
```

`projectArtifacts()` 同样可加：

```ts
projectArtifactsWithReport()
```

### 单项失败规则

```text
readPlacementSpace 整体失败      -> throw（基础设施失败）
单个 CREATE_NODES 失败          -> failures[]，继续下一项
已有 binding 可复用            -> bindings[]
所有 item 都失败                -> 仍返回 degraded report，不要再靠 throw 表达 partial state
```

这样“成功 A + 失败 B”不会丢 A，也不会假装本轮完全成功。

## 1.7 `HostLifecycleReconciler`：degraded 后只自动补跑一次

文件：

```text
apps/web-gen2/src/host/lifecycleReconciler.ts
```

当前 `runNow()` 只：

```ts
await this.runner.runOnce();
return true;
```

它看不到 partial failure，而且 periodic 默认关闭，所以“下一次 reconcile 会补”目前不是保证。

### 改法

把 RunnerLike 收窄：

```ts
export interface RunnerLike {
  runOnce(): Promise<{ readonly degraded?: boolean }>;
}
```

Trigger 增加：

```ts
export type ReconcileTrigger =
  | 'project-open'
  | 'mutation'
  | 'reconnect'
  | 'periodic'
  | 'retry';
```

增加单实例 retry timer：

```ts
private retryTimer: ReturnType<typeof setTimeout> | null = null;
```

在一次真实 run 后：

```ts
const result = await this.runner.runOnce();

if (result.degraded === true && trigger !== 'retry') {
  this.scheduleOneRetry();
}
```

`scheduleOneRetry()` 直接复用现有 cooldown：

```ts
this.retryTimer = setTimeout(
  () => void this.runNow('retry'),
  this.cooldownMs,
);
```

**retry 自己如果仍 degraded，不递归无限 retry。** 后续交给下一次 mutation/reconnect/project-open/periodic。

### 必加测试

```text
first run -> degraded=true
second retry -> degraded=false
=> runner 共 2 次

first run -> degraded=true
retry -> degraded=true
=> 仍然只 2 次，不无限循环
```

## 2.3 在 `metadata-repository.ts` 新增一个原子方法

不要让 Service 自己 `BEGIN/COMMIT`，transaction owner 放在 Repository。

建议 exact symbol：

```ts
confirmContinuationCoreBind(...)
```

输入：

```ts
interface ConfirmContinuationCoreBindInput {
  readonly projectId: string;
  readonly operationId: string;
  readonly expectedRevision: number;
  readonly externalSessionId: string;
  readonly externalEvidence?: ContinuationExternalEvidenceV1;
  readonly fallbackConnectedConversationId: string;
}
```

返回：

```ts
interface ConfirmContinuationCoreBindResult {
  readonly journal: ContinuationOperationJournalRowV1;
  readonly connectedConversation: ConnectedConversationV1;
}
```

### transaction 内顺序

`SqliteMetadataRepository` 当前使用 `node:sqlite DatabaseSync`，直接：

```ts
this.#database.exec('BEGIN IMMEDIATE');
try {
  ...
  this.#database.exec('COMMIT');
} catch (error) {
  this.#database.exec('ROLLBACK');
  throw error;
}
```

transaction 内：

```text
1. SELECT journal
2. assert revision == expectedRevision
3. assert steps.core_bind == pending
4. resolve canonical ConnectedConversation
5. provider 必须一致
6. conversation_ref 唯一性检查
7. INSERT / UPDATE connected_conversations
8. 构造 next journal：
   - connectedConversationId = 真正绑定 id
   - steps.core_bind = confirmed
   - externalEvidence（若有新证据）
   - revision + 1
9. CAS UPDATE continuation_operation_journal
10. COMMIT
```

注意第 8 条：

**当 journal 原来 `connectedConversationId === null`，新建 Core conversation 后必须把真正 id 回写 journal。**

旧 `#writeCoreBind()` 只返回 id，却没有把新 id 写回 journal，这会让 blank/new continuation 后续仍然像“没有 canonical conversation”。

## 2.4 Service 层改法

文件：

```text
apps/local-core/src/conversation-continuation-service.ts
```

`#recoverBind()` 在 provider 返回 `resumed` 后改为：

```ts
const evidence = continuationExternalEvidenceFromReceiptV1(receipt);
const bound = this.metadata.confirmContinuationCoreBind({
  projectId,
  operationId,
  expectedRevision: row.revision,
  externalSessionId: receipt.externalSessionId ?? externalSessionId,
  ...(evidence ? { externalEvidence: evidence } : {}),
  fallbackConnectedConversationId:
    row.connectedConversationId ?? `connected-conversation-${randomUUID()}`,
});
```

然后直接 publish + project fresh journal。

不要再：

```text
#writeCoreBind()
+
advanceStep(core_bind confirmed)
```

`#writeCoreBind()` 可以删除，或只保留成 repository 内 transaction 的私有实现辅助，不能再作为 service 两阶段调用。

### error handling

transaction rollback 后才允许：

```ts
advanceStep(core_bind=failed, expectedRevision=row.revision)
```

**ContinuationStaleRevisionError 不要吞掉改写成 failed。** stale 是并发冲突，不是业务 bind failed，应直接向上抛。
