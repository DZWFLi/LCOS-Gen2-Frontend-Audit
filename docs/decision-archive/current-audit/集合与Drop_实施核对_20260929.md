# Collection / Drop 实施核对（2026-09-29）

## 结论

**现有 Gen2 owner 内可以复用投影、拖放编排与回执模式；不能在不碰 Core/T6 canonical owner 的前提下，完成“向 Collection 添加/移除正式成员”的语义链。** 代码里确有 Scope、ArtifactView、Presentation 和 graph 的写入能力，但原卡明确把 Scope(parentScopeId)、Huabu parentId、Presentation.memberViewIds 及旧 `memberEntityRefs` 排除为 Gen2 Collection membership truth。把其中任一条改名接 UI，会绕过已裁决的 owner 边界。

因此可实施方案分两段：先把 Collection 作为可投影/可承载 Frame 的只读兼容源接到 UI，并复用 Workflow 的 reconcile/host 模式；正式 Drop 在 T6 提供 Collection canonical ref/list/read + add/remove membership transaction 之前保持诚实失败/unsupported。若用户要求本轮完成正式 Drop，就需要 T6/Core owner 变更，而非仅改 T1 UI。

## 可落地顺序与停止条件

1. **可独立做的 T1 UI 部分**：沿 Workflow reconcile/ProjectionBinding 模式增加 Collection 的只读兼容投影与 native Frame host；折叠只影响显示，不写成员 truth；保存展开布局不被自动重排覆盖。对旧 Scope 标识明确标记兼容来源，禁止据此回报正式 membership。
2. **可独立做的 T1 拖放安全部分**：接收 Drop 时先校验目标 Collection 身份与源项目；在没有 T6 command 时返回 `unsupported/membership-owner-unavailable`，保持源对象位置与成员状态不变。成功态只能由 canonical owner receipt 驱动；不以 Huabu reparent 或 Presentation patch 伪造成功。
3. **需要 T6/Core owner 提供后再接通**：Collection canonical ref、list/read（含成员实体身份）、add/remove membership transaction 与幂等/冲突回执；Assembly target/semantic drop dispatch 的 Collection 目标映射；GUI reconciliation 读取同一 owner projection。届时 T1 才能在同一用户动作链里完成“Drop → canonical membership commit → receipt → host projection”。
4. **T2 仍只导航**：Collection click 在原位折叠/展开；浮标、搜索、Rail、返回只读/定位既有实体，不暗中创建 Scope、写 membership 或自动导航到 child canvas。Rail Receive 若目标是 Collection，必须路由到第 3 项 canonical command；当前不支持时明确失败。

### 本轮判定

- **能在现有 T1/UI owner 内实施**：Collection 只读兼容展示、Frame host、展开/折叠视觉态、binding/reconciliation 模式复用、Drop 失败回执与源状态保护。
- **不能在现有 owner 内实施**：新建正式 Collection membership，或宣称旧 Scope/Presentation/graph containment 已构成正式成员链。原卡将该接口明确交给 T6；不应通过复用旧字段绕行。
- **证据边界**：源码存在不等于 GUI 实测；此报告是静态源码/原卡核对，没有运行 Drop、Rail 或持久化验收。
